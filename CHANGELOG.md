# Changelog

All notable changes to *wuzp* are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and *wuzp* follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) (see [CONTRIBUTING.md](CONTRIBUTING.md#versioning)).

## [Unreleased]

### Changed

- **Breaking:** One CMake project and one installable package with the components `eigen`, `blitz`, `boost` and `mp_units`, used as `find_package(wuzp CONFIG REQUIRED COMPONENTS eigen)` and `wuzp::wuzp`, `wuzp::eigen`, etc. It replaces the four separately packaged projects. *wuzp* can also be used through `FetchContent`.
- **Breaking:** Points and vectors (absolute and relative tensors) no longer convert into each other implicitly. Use `makeRelative()` and `makeAbsolute()`.
- **Breaking:** Translations check coordinate systems: an active translation only moves points expressed in its coordinate system, and the vector of a passive translation from `From` to `To` is expressed in `To`. A passive proper rigid transformation declares its translation in `To`.
- **Breaking:** Powers of rationals that are not rationals themselves, such as `4^(1/4)`, are no longer defined (they returned wrong results), and `0^x` is only defined for `x > 0`.
- **Breaking:** `getInvariant(vector)` deduces its template arguments, and takes any vector whose components have the same unit, e.g. a four-velocity. Explicit template arguments no longer compile.
- **Breaking:** With Boost.Units, angles are dimensionless, like with *wuzp*'s own units and mp-units: angular velocity is `1/s`, angular acceleration `1/s^2` and torque `N m`, so the same code compiles with every units backend (see "Angles are dimensionless" in `DESIGN.md`).
- **Breaking:** The template parameters of tensors, quantities, value matrices and transformations are constrained with C++20 concepts (`<wuzp/core/concepts.hpp>`), e.g. the coordinate system of a tensor must be a `CoordinateSystem`. Misuse fails with a constraint error, instead of compiling or failing deep inside the library.
- **Breaking:** Operators and member functions return evaluated values, quantities and tensors, which do not refer to their operands, so that results can be stored in `auto` variables, also when they are computed from temporaries. The traits, e.g. `Sum<Lhs, Rhs>::type`, are still the lazy types. Likewise, `getValues()` and `getQuantities()` of a temporary return its values rather than a reference into it.
- **Breaking:** Value matrix backends specialize the new traits `Copy` and `Move` (`wuzp/core/traits.hpp`), which copy and move their matrices without sharing the values, so that values, quantities and tensors have value semantics with every backend.
- **Breaking:** Conversions that fail their checks, e.g. of a vector in one coordinate system into another one, of a point into a vector, of a length into a time, or of values into values of another size, are explicit: `std::is_convertible` is false for them, and copy initialization fails with a conversion error. Direct initialization still fails with a message that explains why.
- **Breaking:** With mp-units, `wuzp_mp_units::UnitType` normalizes units to the coherent SI units built from the base units, e.g. `si::newton` to `kg m / s^2`, and rejects other units, e.g. kilometres or degrees, since *wuzp* does not convert units.
- **Breaking:** `createBoostMatrix` throws `std::invalid_argument` if the velocity is not smaller than the speed of light.
- **Breaking:** `QuantityI`, `QuantityF` and `QuantityD` are defined by the value matrix backends, e.g. `wuzp_eigen::QuantityD<Length>` instead of `wuzp::QuantityD<Length>`, since they need a value matrix backend. `<wuzp/core/ValueWrapper.hpp>` and `wuzp::ValueWrapper<ValueT>` are removed: use the backend's `Value<ValueT>`, e.g. `wuzp_eigen::Value<double>`. `getSpeedOfLight` takes the value matrix backend: `getSpeedOfLight<wuzp_eigen::ValueMatrix, double>()`.
- **Breaking:** Value matrix backends specialize the traits only for their own matrices and expressions, e.g. `template <EigenArray ImplementationT_>`, and specialize the new traits `Coefficient` (element access) and `Rebind` (values of another value type and size of the same backend). Operations derive scalars from the backend of their operands. See "The backend interface" in `DESIGN.md`.
- **Breaking:** The template parameters that take a value matrix backend, e.g. of `HomogeneousVector`, `PositionVector3` or `ActiveLinearTransformation`, must be the `ValueMatrix` of a value matrix backend (`AnyValueMatrix`), e.g. `wuzp_eigen::ValueMatrix`, not e.g. `Eigen::Array`.
- **Breaking:** With Eigen, evaluated values have Eigen's default storage order, so that results have one type: e.g. the transpose of a `ValueMatrix<double, 3, 2>` is a `ValueMatrix<double, 2, 3>`, rather than a row-major array.
- **Breaking:** Tensors record the variance of each index, in their order: `Tensor<Indices<Up, Down>, Quantities, CoordinateSystem, Absolute>` replaces `Tensor<1, 1, Quantities, CoordinateSystem, Absolute>`, e.g. `Indices<Down, Down>` for a mass matrix. The aliases, e.g. `Vector`, `Covector`, `Point` and `PositionVector3`, are unchanged. The components are stored in a canonical shape: a 1x1 matrix for rank 0, a column for a vector, or several columns for a batch of vectors or points, e.g. a point cloud, a row for a covector, and a square matrix for rank 2 (see "Index variance and order" in `DESIGN.md`). The operations that are only defined for a single vector, e.g. `innerProduct`, `norm()` and `transpose()`, reject batches.
- **Breaking:** `transpose()` swaps the indices: the transpose of a vector is a covector, and that of `T^i_j` is `T_j^i`. `innerProduct` contracts the last index of the left-hand side with the first index of the right-hand side, which must be an upper and a lower index, whatever the shape of the operands: e.g. `innerProduct(v, w)` of a vector and a covector is the scalar `v^i w_i`, and `innerProduct(v.transpose(), innerProduct(M, v))`, which contracts two lower indices, becomes `innerProduct(v, innerProduct(M, v))`. `outerProduct` concatenates the indices of two vectors or covectors, e.g. `outerProduct(v, v)` has two upper indices.
- **Breaking:** `*` and `/` of tensors only take scalars: arithmetic values, values and quantities of size 1x1, and tensors of rank 0. The elementwise products and quotients of tensors of rank 1 or more, and of tensors with quantities or values of other sizes, are rejected: they depend on the basis, so `cwiseProduct` and `cwiseQuotient` compute them as quantities (see "Products of tensors" in `DESIGN.md`).
- **Breaking:** Linear transformations, e.g. rotations and Lorentz transformations, and Jacobians store their matrix as quantities, returned by `getQuantities()`, and are constructed from values or quantities, e.g. `Rotation{tensor.getQuantities()}` rather than `Rotation{tensor}`. `getTensor()` of active linear transformations returns the matrix as a linear map, and only exists for square matrices. Translations provide `getQuantities()` too, and `isApprox` of transformations compares their quantities.
- **Breaking:** Points follow the rules of affine spaces: `p - q` is a vector, `p + v`, `v + p` and `p - v` are points, and the operations whose result depends on the origin of the coordinate system are rejected, e.g. `p * 2.0`, `p * quantity`, `p / quantity`, `-p`, `p.dotProduct(q)`, inner products with a point and its inverse. Affine combinations are written `p + (q - p) * t`. `makeRelative()` of a vector and `makeAbsolute()` of a point are rejected; both are relative to the origin of the coordinate system (see "Points and vectors" in `DESIGN.md`).
- **Breaking:** Only tensors with one upper index, vectors and batches of vectors, can be absolute: e.g. absolute covectors and absolute scalars are rejected. An absolute scalar, e.g. a time point, is a point in a one-dimensional coordinate system, like `TimePoint`. Linear transformations only transform relative covectors.
- **Breaking:** `inverse()` is the matrix inverse of values, quantities and tensors, like Eigen's `MatrixBase::inverse()`. The inverse of a tensor exists for rank 0 and 2, and maps the indices `(X, Y)` to `(not Y, not X)`, e.g. the inverse of a metric `g_ij` is `g^ij`; vectors and covectors have none. The elementwise reciprocal is `cwiseInverse()`, which returns quantities for tensors, like `cwiseProduct`, and also works with Blitz++. The inverse of an integer matrix fails with "The inverse of an integer matrix is not an integer matrix. Use a floating-point value type.", with every value matrix backend: Eigen truncated it before. Value matrix backends specialize the trait `Inverse` for the matrix inverse and the new trait `CwiseInverse` for the elementwise reciprocal (see "Inverses and determinants" in `DESIGN.md`).
- **Breaking:** `determinant()` of a tensor is only defined for tensors of rank 0 and for the mixed tensors of rank 2, e.g. a linear map, whose determinant is invariant. The determinant of a tensor with two upper or two lower indices depends on the basis: `getQuantities().determinant()` computes it. The determinant of quantities is also defined for 1x1 matrices.
- **Breaking:** The matrix inverse and the determinant reject units that do not describe a linear map, `M_ij = a_i / b_j`, with a clear message, also with Boost.Units, which failed with an error without a message before.
- **Breaking:** The passive transformations have no coordinate system parameter any more: they transform tensors expressed in `From`, which the parameter had to equal. E.g. `PassiveSpatialRotation3<ValueMatrix, double, From, To>` replaces `PassiveSpatialRotation3<ValueMatrix, double, From, From, To>`, likewise for `PassiveLinearTransformation`, `PassiveTranslation`, `PassiveSpatialTranslation`, `PassiveProperRigidTransformation` and its template, `Jacobian`, `LorentzTransformation` and `createBoostMatrix`, whose velocity is expressed in `From`. The vector of a passive translation is expressed in `To`. Passive transformations have no `GetCoordinateSystem` or `CastCoordinateSystem` any more, and active linear transformations and translations no `CastCoordinateSystem`.
- **Breaking:** Passive linear transformations, e.g. passive rotations and Lorentz transformations, and Jacobians have no `getTensor()` any more: their matrix maps `From` into `To`, which for a Jacobian may have another dimension, so it is not a tensor in one coordinate system. Use `getQuantities()`. `getTensor()` of active linear transformations, whose square matrices are linear maps in their coordinate system, remains.
- **Breaking:** `transform()` of a transformation no longer takes a passive transformation, nor does `transform()` of a translation or a proper rigid transformation take a linear transformation: these conjugations were wrong or produced transformations that could not be applied. Compose with `*` and `inverse()` instead, e.g. `t * r * t.inverse()` for a rotation `r`. Passing a transformation that `transform()` does not take fails with a message that says to compose transformations with `*`. The other conjugations of active transformations, e.g. of a linear transformation or a translation by a linear transformation, and of a rotation by a rotation, remain; that of a rotation by a linear transformation, which is not a rotation in general, is removed.
- **Breaking:** `isApprox` of transformations compares transformations of the same kind only, checks `From` and `To` of passive transformations, and takes a precision. Comparing passive transformations between different coordinate systems fails with "'From' coordinate systems do not match." or "'To' coordinate systems do not match.", like `operator==`, whose messages for passive translations are now the same.
- **Breaking:** The base class `Transformation` has a protected non-virtual destructor instead of a virtual one, so transformations have no virtual table.
- **Breaking:** `ActiveSpatialRotation`, `PassiveSpatialRotation` and `LorentzTransformation` are classes instead of aliases of linear transformations, with the same template parameters. In debug builds, i.e. if `NDEBUG` is not defined, their constructors check that the matrix is a rotation, `max_ij |(R R^T - I)_ij| <= tolerance` and `det(R) > 0`, or a Lorentz transformation, `Lambda^T eta Lambda = eta`, and throw `std::invalid_argument` otherwise, e.g. for a shear, which was accepted as a rotation. `makeUnchecked()` skips the check, `isValid()` checks with any tolerance, and the default constructors create the identity. They transform the same tensors as before, covectors, linear maps and bilinear forms with their inverse, `R^T` or `eta Lambda^T eta`, instead of the matrix inverse, which adds no rounding errors and also works with integer matrices, and compose with linear transformations into linear transformations. Code that used them as linear transformations converts them, e.g. `ActiveLinearTransformation<...>{rotation.getQuantities()}` (see "Validity of rotations and Lorentz transformations" in `DESIGN.md`).
- **Breaking:** The rotation of `ActiveProperRigidTransformationTemplate` and `PassiveProperRigidTransformationTemplate` must be a rotation (the concept `AnyRotation`), so that their inverse `(R^T, -R^T t)` is right. The templates are defined in `<wuzp/trafo/ActiveProperRigidTransformationTemplate.hpp>` and `<wuzp/trafo/PassiveProperRigidTransformationTemplate.hpp>`, which the headers of the aliases include.
- **Breaking:** `Jacobian` is a class of its own instead of an alias of `PassiveLinearTransformation`, with the same template parameters. It maps tangent objects, not points: `transform()` pushes forward relative vectors, `J v`, e.g. velocities, and tensors with two upper indices, `J T J^T`, e.g. covariances, and rejects points ("A Jacobian maps vectors, not points: ..."), which it mapped like a change of basis, and covectors and the other tensors, which it transformed with its inverse, only for square Jacobians ("... Use pullback() for covectors and tensors with two lower indices."). `inverse()` only exists for square Jacobians. Jacobians compose by the chain rule with Jacobians and, in both orders, with passive linear transformations, rotations and Lorentz transformations into Jacobians, e.g. `rotationEW * jacobianWQ`, and no longer into linear transformations (see "Jacobians" in `DESIGN.md`).
- **Breaking:** `PassiveLinearTransformation` is a change of basis, whose matrix is square, so it has one dimension parameter, like the rotations and the Lorentz transformations: e.g. `PassiveLinearTransformation<ValueMatrix, double, From, To, 3, Dimensionless>` replaces `PassiveLinearTransformation<ValueMatrix, double, From, To, 3, 3, Dimensionless>`. A linear map between coordinate systems of different dimensions is a `Jacobian`.
- **Breaking:** A coordinate system has a metric, its second template parameter, `Euclidean` by default or `Minkowski`, e.g. `CoordinateSystem<Spacetime, Minkowski>`. `dotProduct`, `norm`, `squaredNorm`, `crossProduct` and `transpose()` of a vector or a covector use the Euclidean metric, so they fail in other coordinate systems with "dotProduct, norm, squaredNorm, crossProduct and the transpose of a vector or a covector use the Euclidean metric, which this coordinate system does not have. ...": in a Minkowski coordinate system, `innerProduct` pairs a covector and a vector without a metric (see "Metric" in `DESIGN.md`).
- **Breaking:** `SpacetimeVector` and `SpacetimePoint` are constrained to coordinate systems with the Minkowski metric (`MinkowskiCoordinateSystem`), and `getInvariant()` requires one, so that the Euclidean dot product and norm of a spacetime vector, which Lorentz transformations do not preserve, are rejected. The velocity that `createBoostMatrix` takes is expressed in `From`, such a coordinate system, so its `norm()` is rejected too: its magnitude is `velocity.getQuantities().norm()`.
- **Breaking:** `LorentzTransformation` and `createBoostMatrix` transform between coordinate systems with the Minkowski metric (`MinkowskiCoordinateSystem`), and `ActiveSpatialRotation`, `PassiveSpatialRotation`, `ActiveProperRigidTransformationTemplate` and `PassiveProperRigidTransformationTemplate`, and thus the proper rigid transformations, between coordinate systems with the Euclidean metric (`EuclideanCoordinateSystem`), the metrics that define them: other coordinate systems fail with a constraint error. A spatial rotation of spacetime is a `LorentzTransformation`.
- **Breaking:** The core defines the sum and the difference of units for every units backend, and rejects different units with "Units do not match.", also with Boost.Units, which failed with an error without a message before. Units backends no longer specialize `Sum` and `Difference` for their units.
- **Breaking:** The backend concepts require what the core uses: `UnitSystem` rational powers of units (`Power` with `Rational<P, Q>`, e.g. for `pow<1, 2>()`), `InvertibleValueMatrixBackend` the determinant of integer matrices, and `ValueMatrixBackend` matrices that can be default constructed and moved, and constructed from the lazy results of the traits, which must be move constructible. The constructor of values passes the elements to the trait `Initialize` as values of the value type, as `ValueMatrixBackend` checks, rather than with their own types, e.g. `const int&`.
- **Breaking:** The elements that values, quantities and tensors are constructed from, or that `set()` and `setValue()` set, are converted into the value type like the scalars of operations: only if the common type of an element and the value type is the value type, e.g. an `int` element for `double` values. Other elements fail with "The common type of the element and the value type is not the value type, e.g. a double element with int values.", e.g. `ValueMatrix<int, 1, 1>{1.5}` or `set(1.5)` on `int` values, which were truncated to `1`, or `ValueMatrix<float, 2, 1>{1.0, 2.0}`: use `float` elements, e.g. `{1.0F, 2.0F}`.
- **Breaking:** `sin()` and `cos()` of an angle with integer values fail with "sin and cos need floating-point values.": their results are not integers in general.
- `pow<P, Q>()` of a negative value with an odd reduced denominator `Q` is the real root `(-1)^P |x|^(P/Q)`, e.g. `pow<1, 3>()` of `-8 m³` is `-2 m`, instead of NaN. With an even `Q`, it is NaN for floating point values, like `std::pow`, and throws `std::domain_error` for integer values, which converted NaN into an integer, undefined behavior (see "Powers of negative quantities" in `DESIGN.md`).
- Translations move a single point by adding the translation to it, instead of component by component, which is faster and also works for points with different units per component.
- The oldest supported dependency versions are those of Ubuntu 22.04: GCC 11, Clang 14, CMake 3.22, Eigen 3.4 and Boost 1.74.

### Added

- The trait `Metric<CoordinateSystem>`, the metric tags `Euclidean` and `Minkowski`, and the concepts `EuclideanCoordinateSystem` and `MinkowskiCoordinateSystem` (see "Metric" in `DESIGN.md`).
- `ForceCovector`, `ForceCovector2` and `ForceCovector3`: a force as a covector, the dual of a velocity, which a Jacobian pulls back. A `ForceVector` is pulled back as its transpose, `jacobian.pullback(force.transpose())`.
- `DESIGN.md` documents the cross product as a pseudovector, the three meanings of moving frames (the basis a quantity is expressed in, the frame it is measured in and the point it is about), the relative comparison of `isApprox()`, and angles as quantities with the unit one, in the wording of the SI Brochure, with their known risks.
- `Jacobian::pullback()` pulls covectors, `w J`, e.g. a force into the joint torques `J^T F`, and tensors with two lower indices, `J^T M J`, e.g. a Cartesian mass matrix into the joint space inertia, back from `To` to `From`, also for Jacobians that are not square. With `transform()` and the inverse of tensors, it computes e.g. the operational space inertia of Khatib, `jacobian.transform(massMatrix.inverse()).inverse()`.
- Translations leave covectors and tensors with two upper indices, e.g. covariances, unchanged, like vectors, so proper rigid transformations transform them by their rotation, `w R^T` and `R S R^T`. They did not compile before. Translations reject the other tensors, e.g. an inertia, which may depend on the origin, with "A translation only transforms points, vectors, covectors and tensors with two upper indices: other tensors may depend on the origin, e.g. an inertia about it." (see "Translations of tensors" in `DESIGN.md`).
- An [mp-units](https://mpusz.github.io/mp-units/) units backend, the `mp_units` component, for mp-units 2.5 or newer.
- Support for Eigen 5, besides Eigen 3.4.
- Support for macOS (Apple Clang) and, on a best-effort basis, Windows (MSVC), both tested in CI.
- A guide to writing a backend, "Writing a backend" in `CONTRIBUTING.md`, with minimal example backends: the archetypes of the tests, which provide exactly what the concepts of the backend interface require. The tests run against them in CI (the presets `gcc-archetype-archetype` and `clang-archetype-archetype`), which checks that *wuzp* uses nothing beyond the concepts.
- `<wuzp/wuzp.hpp>` includes all headers of the core and the transformations.
- Benchmarks that compare *wuzp* with plain Eigen and Blitz++ at run time, and with plain Eigen at compile time (`benchmarks/README.md`).
- Linear transformations transform covectors (`w' = w A^-1`) and tensors with two contravariant indices (`T' = A T A^T`). They returned `void` before.
- `zero()` and `random()` for values, quantities and tensors, with every backend. They did not compile before.
- Concepts for the backend interface, `ValueMatrixBackend`, `InvertibleValueMatrixBackend` and `UnitSystem` (`<wuzp/core/concepts.hpp>`). The tests check every backend with them, and authors of other backends can do the same, so that a backend that misses a trait fails in its tests, rather than deep inside the core.
- Several value matrix backends can be used in one program, also in one translation unit. A program uses exactly one units backend.
- Compile tests verify that invalid code does not compile, and that the error message explains why.
- The public headers compile on their own and without warnings with `-Wshadow -Wconversion -Wsign-conversion -Wold-style-cast`.
- `cwiseProduct` and `cwiseQuotient` of tensors, which return the elementwise product and quotient of their components as quantities, and the elementwise `division` of quantities of the same size.
- Products of tensors of rank 0 with tensors of any rank, e.g. of a scalar field and a vector.
- Quantities and tensors can be multiplied and divided by arithmetic scalars of another type, if their common type is the value type, e.g. `2 * v` for a vector of `double`.
- The trait `UnitsDescribeLinearMap`, which checks that the units of a matrix describe a linear map, `M_ij = a_i / b_j`.
- Composition of transformations with `*`: `lhs * rhs` applies `rhs` first, then `lhs`. Passive transformations compose in the order of Drake's monogram notation, `X_AB * X_BC = X_AC`, and the coordinate systems that meet must match ("Adjacent frames do not match."); active transformations compose within their coordinate system. Linear transformations compose with linear transformations (the product of their matrices), Jacobians with Jacobians and with passive linear transformations, including rotations and Lorentz transformations, into Jacobians (the chain rule), rotations with rotations into rotations, Lorentz transformations with Lorentz transformations into Lorentz transformations, translations with translations, and proper rigid transformations, rotations and translations with each other into proper rigid transformations. Other combinations, e.g. a translation with a scaling, fail with "These transformations cannot be composed." (see "Composition and inverse of transformations" in `DESIGN.md`).
- `inverse()` of every transformation: the matrix inverse for linear transformations, the transpose for rotations, `eta Lambda^T eta` for Lorentz transformations, `-t` for translations and `(R^T, -R^T t)` for proper rigid transformations. A passive inverse transforms from `To` to `From`.
- `projectToRotation()` of `ActiveSpatialRotation` and `PassiveSpatialRotation`, which computes the rotation nearest to a matrix close to a rotation, e.g. one whose rounding errors accumulated, by the Newton-Schulz iteration, with every value matrix backend.
- The trait `ValidityTolerance`, the tolerance of the validity checks of rotations and Lorentz transformations: `1e-9` for `double`, `1e-4` for `float` and `0` for `int`, separate from the precision of `isApprox()`.
- Matrix inverses and determinants with Blitz++, computed by Gauss-Jordan elimination with partial pivoting: the Blitz++ backend satisfies `InvertibleValueMatrixBackend`, so `inverse()` and `determinant()` of values, quantities and tensors, the inverses of linear transformations and the transformations of covectors, linear maps and bilinear forms work with Blitz++ too. The inverse of a singular matrix is NaN, its determinant zero (see "Backend support for inverses" in `DESIGN.md`).

### Removed

- `getTypeName()`, which returned wrong names.
- The trait `AccessValues`, the global default value matrix backend, which `Rebind` replaces.
- `tensorProduct` and the trait `TensorProduct`, which no backend implemented and which gave the result the indices of the left operand: `outerProduct` is the tensor product.
- `IsSpecializationInts`, which `IsSpecialization` replaces now that the template parameters of `Tensor` are types.
- `tensorInverse()` and the trait `TensorInverse`: `inverse()` is the matrix inverse.
- The aliases `Copoint` and `HomogeneousCopoint`: covectors cannot be absolute.
- The unused specialization of `Identity` for Boost.Units' absolute units.

### Fixed

- The units of `TimePoint`, `Duration` and `TorqueVector`.
- Determinants have the product of the diagonal units.
- `Tensor::isApprox` checks the covariant indices.
- The homogeneity check of `Quantities`: elements with mixed units could be set with runtime indices.
- The Lorentz invariant read freed memory, and the Lorentz boost matrix was NaN for zero velocity.
- With Blitz++: `isApprox` compares relatively, like with Eigen; the dot product read a freed temporary; inner products and norms keep the value type of the operands instead of widening it, and inner products no longer copy an uninitialized member of Blitz++'s lazy reductions.
- Reducing rationals with large denominators exceeded the template instantiation depth.
- Including both value matrix backends in one translation unit was a redefinition error, and using them in different translation units of one program violated the one definition rule.
- Translations did not compile with Clang 20 and newer.
- `Tensor::hyperdeterminant` failed with a confusing error instead of "Not implemented".
- `sin()` and `cos()` looked up the units for the type of the values rather than for their value type, e.g. `double`, which only worked with units backends that specialize `AccessUnits` for every type.
- With Clang 14, `ValueMatrixBackend` instantiated `Random` also for integer matrices, so it failed for backends that only provide random floating point values.
- With Blitz++, copies of values, quantities and tensors shared their values with the original, so translations changed their `const` input point, and transposes and blocks changed with the original. They have value semantics with every backend now; with Blitz++, a moved-from object is empty and can only be assigned to or destroyed ([#60](https://github.com/remod/wuzp/issues/60)).
- Dividing tensors did not check their coordinate systems ([#61](https://github.com/remod/wuzp/issues/61)).
- Converting values of another size, e.g. constructing a 3D vector from two values or calling `setValues()` with values of another size, was not checked, and read past the values with Blitz++. It fails with a message now ([#62](https://github.com/remod/wuzp/issues/62)).
- `pow<1, 2>()` of an integer quantity returned 1: non-integer exponents are computed in floating point, and the result is converted to the value type, which truncates like the norm of integer vectors ([#63](https://github.com/remod/wuzp/issues/63)).
- Operations on the results of operations did not compile: `-(a + b)`, `sin(a + b)`, `cos(a + b)`, `translation.transform(p + v)`, and with Blitz++ the dot product, transpose and blocks of expressions ([#64](https://github.com/remod/wuzp/issues/64)).
- With mp-units, named units such as `si::newton`, `si::joule` and `si::hertz` did not match the units *wuzp* computes ([#65](https://github.com/remod/wuzp/issues/65)).
- Copying a transformation, a tensor, quantities or values from a non-const object used the forwarding constructor, which did not compile for transformations ([#66](https://github.com/remod/wuzp/issues/66)).
- The Lorentz boost returned NaN for velocities of at least the speed of light. It is documented that the velocity is the one of `To` relative to `From`, expressed in `From` ([#67](https://github.com/remod/wuzp/issues/67)).
- Whether a result referred to its operands depended on the operator: `auto x = makeVector() / QuantityD<Dimensionless>(2.0);` read a destroyed temporary, `makeVector() / 2.0` did not ([#69](https://github.com/remod/wuzp/issues/69)).
- Type traits reported invalid conversions as valid, e.g. `std::is_convertible` of a vector in one coordinate system into another one, which made overloads ambiguous ([#70](https://github.com/remod/wuzp/issues/70)).
- `isApprox` of transformations was not `const`, had no precision parameter, did not check `From` and `To` of passive transformations, and did not compile for proper rigid transformations ([#68](https://github.com/remod/wuzp/issues/68)).
- Translations transformed a linear transformation `Q` into itself, and proper rigid transformations into `R Q R^-1`, ignoring their translation, but `T Q T^-1` is the affine map `x -> Q x + (I - Q) t`: e.g. for `t = (0, 0, 1)` and a rotation by `pi` around `x`, it maps `(0, 0, 1)` onto itself, not to `(0, 0, -1)`. The conjugation is removed; `t * q * t.inverse()` computes it ([#72](https://github.com/remod/wuzp/issues/72)).
- Passive transformations transformed by passive transformations could not be applied, since their coordinate system parameter had to equal `From`. The parameter and these transformations are removed; composition and `inverse()` replace them ([#73](https://github.com/remod/wuzp/issues/73)).
- `DESIGN.md` claimed that active and passive transformations with the same parameters cancel each other, which for proper rigid transformations only holds with the translation `-R^T t` of the passive transformation, expressed in `To`, not `-t`. It is documented and tested.
- The index rules of `innerProduct` were unsound: the inner product of a vector and a covector was a 3x3 matrix typed as a scalar, and inner products contracted two upper indices ([#71](https://github.com/remod/wuzp/issues/71)). `outerProduct(v, v)` of two vectors failed with "Hypermatrices are not supported".
